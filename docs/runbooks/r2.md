# Cloudflare R2 配置与运维

## 环境与 Bucket 隔离

分别创建并保持为私有的 Bucket：`nomo-dev`、`nomo-staging`、`nomo-production`。每个环境使用独立的 Cloudflare R2 API Token、独立的 Supabase 项目及独立的 Vault secret；不得复用生产 Bucket、Token 或凭证到开发和预发布环境。

为每个 Bucket 创建一个仅限该 Bucket 的 Cloudflare R2 API Token，权限选择 **Object Read & Write**。不要授予账户级的额外权限，也不要把 Token 或 S3 凭证写入代码、配置文件、终端历史或日志。

## Supabase Vault

在对应环境的 Supabase Dashboard Vault 中创建以下四个名称，值从受管密码库粘贴。名称必须完全一致：

- `r2_account_id`
- `r2_bucket_name`
- `r2_access_key_id`
- `r2_secret_access_key`

此文档不保存任何 secret 值。应用数据库 RPC 从 Vault 读取这些值；客户端不得获得它们。

## R2 CORS

`nomo-dev` 本地开发 Bucket 可直接使用以下配置；它只允许 Vite 本地 Origin：

```json
[
  {
    "AllowedOrigins": ["http://localhost:5173"],
    "AllowedMethods": ["GET", "HEAD", "PUT"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 300
  }
]
```

不要把这份开发 CORS 配置复用到生产环境。配置预发布或生产 Bucket 前，操作人员必须取得该次部署实际使用的 `VITE_PUBLIC_APP_ORIGIN`，确认它是单个 HTTPS Origin（不能包含路径、查询参数或片段），再为对应 Bucket 生成只含该 Origin 的配置并人工复核。以下模板不会提供可误用的占位域名；将实际值放入 `NOMO_APP_ORIGIN` 后运行：

```sh
if [ -z "${NOMO_APP_ORIGIN:-}" ]; then
  echo "NOMO_APP_ORIGIN must equal the deployed VITE_PUBLIC_APP_ORIGIN" >&2
  exit 1
fi

if ! printf '%s' "$NOMO_APP_ORIGIN" | jq -eR 'test("^https://[A-Za-z0-9.-]+(:[0-9]{1,5})?$")' >/dev/null; then
  echo "NOMO_APP_ORIGIN must be one HTTPS origin without a path, query, or fragment" >&2
  exit 1
fi

jq -n --arg origin "$NOMO_APP_ORIGIN" '[{
  AllowedOrigins: [$origin],
  AllowedMethods: ["GET", "HEAD", "PUT"],
  AllowedHeaders: ["Content-Type"],
  ExposeHeaders: ["ETag"],
  MaxAgeSeconds: 300
}]' > r2-cors.json
```

应用前检查 `r2-cors.json` 只有一个 Origin，且与部署的 `VITE_PUBLIC_APP_ORIGIN` 完全一致；不要使用 `*`，不要在不同环境之间复用 CORS。应用后再次确认 Bucket 仍为私有。

## 数据库迁移与 pgTAP

由具备数据库变更权限的人员按顺序执行迁移：`202607290001_core_schema.sql` → `202607290002_security_and_search.sql` → `202607290003_r2_media_rpc.sql`。本仓库不会自动创建或修改数据库。

在已应用上述迁移后，手动运行 `004_r2_signing.test.sql`。`005_media_rpc.test.sql` 只能在 Vault 为空的隔离、一次性测试数据库中单独运行，绝不可针对已经配置凭证的开发共享环境、预发布环境或生产环境执行。

`005_media_rpc.test.sql` 会先验证四个固定名称均不存在，再在事务内创建固定名称的测试 secret，最后通过回滚移除这些测试数据。因此它不要求 secret 预先存在；若 Vault 已包含任一同名 secret，测试应立即失败，不要删除或覆盖现有 secret 来运行测试。

## 签名 URL 行为

上传与下载签名 URL 的有效期均为 5 分钟（300 秒）。PUT URL 的 `Content-Type` 已被签名：上传请求必须发送与 RPC 请求完全相同的 `Content-Type`。URL 过期、方法篡改或内容类型不匹配时应被 R2 拒绝；客户端应重新请求会话或下载 URL，而不是重试旧 URL。

绝不记录、分析或分享完整的签名 URL；它们包含临时授权信息。同样不得记录 Vault secret、R2 Token 或访问密钥。

## 密钥轮换

按以下顺序轮换每个环境的 R2 凭证：

1. 在该环境对应 Bucket 上新增一个 Object Read & Write 凭证。
2. 更新该环境 Supabase Vault 的 `r2_access_key_id` 与 `r2_secret_access_key`，保留相同的 Vault 名称。
3. 使用该环境的应用验证一次签名 PUT 上传与签名 GET 下载；检查 URL 过期后会被拒绝，且不记录 URL。
4. 验证完成后撤销旧凭证。

若验证失败，保留旧凭证以维持服务，修正 Vault 配置后重新验证；不要通过放宽 Bucket 权限、CORS 或跨环境复用凭证来恢复服务。
