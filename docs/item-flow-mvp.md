# Nomo 物品流转与状态 MVP 落地方案

## 1. 目标

让 Nomo 从“记录物品原本放在哪里”的静态清单，升级为能够回答以下问题的动态系统：

- 物品现在是否仍在原位？
- 有多少件已经被取出？
- 谁或什么用途正在使用它？
- 物品是否已经放回？
- 物品是否被移动到了另一个箱子？

该能力不预设“家庭”或“公司”等组织关系。家、公司、工作室、仓库继续统一使用现有的“场地 → 空间 → 箱子 → 物品”模型。

## 2. MVP 范围

第一期只建立一个可靠、低摩擦的闭环：

> 扫描或打开箱子 → 取出／放回／移动物品 → 立即更新当前状态 → 保留流转记录。

### 2.1 支持的操作

1. **取出**
   - 选择取出数量。
   - 可选填写“经手人／用途”。这里使用自由文本，不依赖成员系统。
   - 取出后显示“部分取出”或“已取出”。

2. **放回**
   - 选择放回数量。
   - 默认放回物品当前所属箱子。
   - 不能放回超过已取出的数量。

3. **移动**
   - 第一期只支持整项移动，即该物品的全部数量移动到另一个箱子。
   - 存在未放回数量时不能移动，避免当前位置语义不明确。
   - 目标箱子按场地、空间分组选择。

4. **流转记录**
   - 显示操作类型、数量、时间、原箱子、目标箱子以及可选经手人／用途。
   - 记录不可由客户端直接修改或删除。

### 2.2 当前状态

每个物品显示以下状态之一：

- **在位**：全部数量在所属箱子中。
- **部分取出**：仍有部分数量在箱中。
- **已取出**：箱中数量为零。

“已移动”不是持续状态，而是一条流转记录；移动完成后，物品在新箱子中重新显示为“在位”。

## 3. 暂不纳入第一期

- 家庭成员、公司成员或组织权限。
- 审批、评论、聊天和通知中心。
- 预约借用、逾期催还和日历提醒。
- 同一物品部分数量移动到另一个箱子。
- 跨账号转让物品。
- 自动盘点、蓝牙或 RFID 硬件。

这些能力不能阻塞 MVP。第一期仍沿用当前 owner 权限；后续多人能力只需扩展授权层，不改变流转模型。

## 4. 数据模型

### 4.1 `items` 增加字段

```sql
stored_quantity integer not null
```

语义：当前仍在物品所属箱子中的数量。

约束：

```sql
stored_quantity >= 0
stored_quantity <= quantity
```

迁移现有数据时，所有记录设置为：

```sql
stored_quantity = quantity
```

新建物品时由数据库触发器自动设置 `stored_quantity = quantity`，客户端不直接写入该字段。

显示状态由客户端或查询函数派生，不额外存储状态枚举：

```text
stored_quantity = quantity  → 在位
0 < stored_quantity < quantity → 部分取出
stored_quantity = 0 → 已取出
```

这样可以避免状态和数量互相矛盾。

编辑总数量时必须保留“已取出数量”不变：

```text
out_quantity = old.quantity - old.stored_quantity
new.stored_quantity = new.quantity - out_quantity
```

如果 `new.quantity < out_quantity`，数据库拒绝更新。这样增加总数量代表新增物品已经入箱，减少总数量则优先减少箱中数量，不会凭空将已取出的物品标记为已归还。

### 4.2 新增 `item_movement_action`

```sql
take_out
return
move
```

### 4.3 新增 `item_movements`

建议字段：

| 字段 | 用途 |
|---|---|
| `id` | 流转记录 ID |
| `item_id` | 对应物品 |
| `actor_id` | 当前操作账号 |
| `action` | 取出、放回或移动 |
| `quantity` | 本次操作数量 |
| `from_box_id` | 原箱子；取出和移动必填 |
| `to_box_id` | 目标箱子；放回和移动必填 |
| `handler_label` | 可选经手人／用途，自由文本 |
| `note` | 可选备注 |
| `created_at` | 操作时间 |

关键约束：

- `quantity > 0`。
- 取出：有 `from_box_id`，无 `to_box_id`。
- 放回：无 `from_box_id`，有 `to_box_id`。
- 移动：同时有 `from_box_id` 和 `to_box_id`，且二者不同。
- 客户端只能读取，不能直接写入或删除流转记录。
- `from_box_id` 和 `to_box_id` 在箱子删除时使用 `on delete set null`；删除物品时历史随物品级联删除。

### 4.4 原子操作 RPC

所有状态变化通过数据库函数完成，避免并发操作导致数量错误：

```text
take_out_item(item_id, quantity, handler_label?, note?)
return_item(item_id, quantity, note?)
move_item(item_id, target_box_id, note?)
```

数据库函数需要：

1. 锁定物品记录。
2. 验证当前用户拥有源箱子和目标箱子。
3. 验证数量边界。
4. 更新 `stored_quantity` 或 `box_id`。
5. 插入一条 `item_movements`。
6. 在同一事务中完成并返回更新后的物品状态。

## 5. 与现有架构的关系

### 5.1 可直接复用

- `items.quantity` 继续表示物品总数量。
- `items.box_id` 继续表示物品当前归属箱子。
- 现有箱子二维码和 `/b/:publicId` 页面继续作为快捷入口。
- 现有 `activity_logs` 保留通用增删改审计。
- 现有 RLS 继续以箱子 owner 为权限基础。
- 现有移动端 Action Sheet 用于承载快速操作。

### 5.2 需要扩展

- `ItemRecord`、公开箱子 RPC 和搜索 RPC 返回 `stored_quantity`。
- 物品列表增加状态和“箱中数量／总数量”。
- owner 在箱子详情中获得“取出、放回、移动、流转记录”操作。
- 公共只读访问只能看到数量状态，不能看到经手人、备注和流转历史。
- 搜索结果显示当前是否在位，避免用户找到一个实际已被取出的物品。

## 6. 交互方案

### 6.1 箱子详情

每个物品行新增轻量状态信息：

```text
在位 · 3/3
部分取出 · 1/3 在箱中
已取出 · 0/1 在箱中
```

owner 点击物品后进入操作面板：

- 取出
- 放回（仅存在已取出数量时显示）
- 移动到其他箱子
- 查看流转记录
- 编辑物品
- 删除物品

### 6.2 取出与放回

- 数量为 1 时，一次点击确认即可完成。
- 数量大于 1 时显示步进器，默认操作 1 件。
- 经手人／用途和备注放在“更多信息”中，避免增加默认操作成本。
- 成功后关闭面板、刷新物品状态并显示轻量反馈。

### 6.3 移动

- 目标选择器只显示当前用户拥有的其他箱子。
- 按“场地 → 空间”分组，避免同名箱子难以识别。
- 清晰显示移动路径：`原场地 / 原空间 / 原箱子 → 新场地 / 新空间 / 新箱子`。
- 操作前说明“将移动该物品的全部数量”。

### 6.4 扫码

- 扫码仍然打开箱子详情，不新增独立扫描协议。
- owner 扫码后可直接操作箱内物品。
- 非 owner 或匿名访问保持只读。

## 7. API 与前端模块建议

新增目录：

```text
apps/web/src/features/item-movements/
```

建议模块：

- `item-movements.api.ts`
- `item-movement-status.ts`
- `ItemMovementSheet.tsx`
- `ItemMovementHistory.tsx`
- 对应单元测试

API：

```ts
takeOutItem(input)
returnItem(input)
moveItem(input)
listItemMovements(itemId)
```

查询 key：

```text
['item-movements', itemId]
['box', publicId]
['items', boxId]
['boxes']
['search-items', query]
```

操作成功后至少刷新当前箱子；移动操作还需要刷新目标箱子和箱子目录统计。

## 8. 数据库与安全要求

- RPC 必须拒绝负数、零、超出可取出数量和超出可放回数量的请求。
- 移动必须验证源箱子和目标箱子属于同一当前用户。
- 流转表开启 RLS，只允许物品所属箱子的 owner 读取。
- 禁止 authenticated 角色直接 `insert/update/delete item_movements`。
- 禁止客户端直接更新 `items.stored_quantity`，仅允许触发器和流转 RPC 修改。
- 普通物品数量更新由数据库触发器同步 `stored_quantity` 并保持已取出数量不变。
- 公共箱子 RPC 不返回 `handler_label` 和 `note`。
- 删除箱子或物品时，历史记录默认级联删除；第一期不承担长期合规审计职责。
- 并发取出通过 `select ... for update` 保证不会出现负数。

## 9. 测试与验收标准

### 9.1 数据库测试

- 现有物品迁移后 `stored_quantity = quantity`。
- 取出、放回和移动均写入一条正确记录。
- 不能取出超过在箱数量。
- 不能放回超过已取出数量。
- 存在取出数量时不能移动。
- 不能移动到其他用户的箱子。
- 匿名用户不能执行流转或读取历史。
- 并发请求不会导致 `stored_quantity < 0`。

### 9.2 前端测试

- 三种状态文案和数量正确。
- 数量为 1 时保持快速操作。
- 操作失败使用现有全局错误反馈，不改变页面布局。
- 移动成功后物品从源箱子消失并出现在目标箱子。
- 搜索结果显示更新后的状态。
- owner、非 owner、匿名三种访问权限正确。
- 移动端操作面板支持键盘焦点恢复和安全区。

### 9.3 产品验收

完成以下路径即视为 MVP 闭环成立：

1. 用户扫描箱子二维码。
2. 打开某个物品，取出 1 件。
3. 页面立即显示剩余在箱数量。
4. 用户再次打开并放回 1 件。
5. 状态恢复为“在位”。
6. 流转记录中存在对应的取出和放回事件。
7. 用户可以将全部在位物品移动到另一个箱子。

## 10. 分阶段实施顺序

### Phase 1：数据基础

- 新增迁移、枚举、`stored_quantity` 和 `item_movements`。
- 新增三个原子 RPC 与数据库测试。
- 更新手工维护的数据库类型。

### Phase 2：前端领域层

- 新增流转 API、状态派生函数和测试。
- 扩展箱子详情、公开箱子和搜索返回类型。

### Phase 3：核心交互

- 在箱子详情加入状态展示和流转操作面板。
- 实现取出、放回、移动与操作反馈。
- 保证扫码进入后的操作路径不超过三步。

### Phase 4：历史与搜索

- 加入物品流转记录。
- 搜索结果展示在位状态。
- 完成移动端和桌面端布局统一。

### Phase 5：回归与发布准备

- 运行数据库测试、全量前端测试、类型检查、Lint 和生产构建。
- 验证旧数据迁移、匿名访问、owner 操作与移动端流程。
- 更新产品文档与数据库部署说明。

## 11. 后续演进

MVP 稳定后再评估：

- 借用到期时间与提醒。
- 常用经手人建议。
- 部分数量跨箱移动与物品拆分／合并。
- 场地级成员与角色权限。
- 流转统计、耗材预警和盘点任务。

这些能力都建立在同一份流转账本之上，因此无需在第一期提前引入组织模型。
