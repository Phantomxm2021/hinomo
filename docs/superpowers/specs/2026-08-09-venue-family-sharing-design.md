# 场所家庭共享与物品流转记录设计

## 1. 文档状态

- 状态：已确认，待实施计划
- 日期：2026-08-09
- 方案：场所成员关系表，保留现有单一 `owner_id` 数据所有权模型
- MVP 人数上限：每个场所最多 5 人，包含 1 位所有者和最多 4 位成员

## 2. 背景与目标

Nomo 当前以单个账号为数据边界：场所、空间、箱子及媒体直接使用 `owner_id = auth.uid()`，物品等子实体通过所属箱子的所有者授权。家庭实际收纳却通常由多人共同完成，单一账号会造成密码共享、操作来源不清和成员离开后无法安全撤权。

本功能允许场所所有者通过一次性链接或二维码邀请家人。成员使用自己的 Nomo 账号进入共享场所，可以独立查看、搜索、扫码和维护收纳内容；系统保留关键物品流转记录，让所有者知道“谁在何时做了什么”。

目标：

- 以“场所”为最小共享范围，不共享账号下的其他场所；
- 每位成员使用自己的账号，不共享密码或支付能力；
- 成员可完成日常收纳操作，危险操作仍由场所所有者控制；
- 箱子额度归属、AI Credits 消耗及操作日志均有明确主体；
- 邀请、加入、移除和并发操作由数据库强制保证安全；
- 在不重写现有数据所有权模型的前提下上线，并保持原有单人场所行为不变。

## 3. 范围与非目标

### 3.1 本期范围

- 场所级成员关系及最多 5 人限制；
- 单次使用、24 小时有效的邀请链接与二维码；
- 共享场所的读取、搜索、扫码及受控编辑；
- 成员创建箱子时使用场所所有者的箱子额度；
- 成员执行 AI 识别时使用成员本人的 AI Credits；
- 关键物品流转记录、成员和动作筛选；
- 成员移除、主动退出及即时撤权；
- 中英文、移动端、无障碍、安全、测试、监控和发布方案。

### 3.2 非目标

- 不建立跨场所的“家庭/组织”工作区；
- 不支持逐箱子或逐物品分享；
- 不支持只读、儿童等更多角色，MVP 仅有所有者和成员；
- 不支持转让场所所有权；
- 不允许场所所有者退出自己的场所；
- 不共享或合并家庭 AI Credits；
- 不提供实时通知、推送或邮件提醒；
- 不修改公开箱子、公开搜索的既有可见性含义；
- 不恢复已经删除的数据，也不将活动记录设计为完整审计归档产品。

## 4. 方案选择

采用“场所所有者 + 场所成员关系表”。`venues.owner_id` 继续是唯一所有者，现有场所、空间、箱子、物品和媒体的归属不迁移；新增 `venue_members` 表只表达额外访问权。

选择原因：

- 与现有 `owner_id`、RLS、箱子额度和媒体路径兼容；
- 可以逐条改造场所访问路径，发布和回滚风险较小；
- 所有者仍是付款、额度及危险操作的唯一责任主体；
- 将来可在成员关系上增加角色，而不改变本期数据归属。

未采用：

- “家庭工作区”作为新的顶层所有者：长期更通用，但要求迁移全部实体、账单和媒体归属，超出 MVP；
- 让分享令牌直接成为长期访问凭证：无法可靠识别操作者、撤销个人访问或形成可信流转记录；
- 复用所有者账号登录：存在密码、支付和隐私风险，且不能区分实际操作者。

## 5. 核心产品规则

1. 一个场所始终只有一位所有者，记录在 `venues.owner_id`。
2. 所有者不重复写入成员表；每个场所最多有 4 条有效成员记录，因此总人数最多 5 人。
3. 成员权限覆盖共享场所及其空间、箱子、物品、相关媒体和收纳流程，不延伸至所有者的其他场所。
4. 成员创建的业务数据仍归场所所有者：带 `owner_id` 的新记录使用 `venues.owner_id`，物品等无 `owner_id` 的子实体通过其规范父记录归属所有者。
5. 日志的 `actor_id` 必须是实际操作的账号，不得写成场所所有者。
6. 成员创建箱子消耗场所所有者的免费箱子名额；所有者已永久解锁时成员也可继续创建。
7. 成员使用 AI 功能时消耗操作者自己的 AI Credits，不消耗所有者余额。
8. 所有者可移除任意成员；成员可主动退出。两者都不删除场所数据或历史日志。
9. 成员退出或被移除后立即失去访问权；已打开页面的下一次数据库请求也必须被拒绝。
10. 现有未共享场所维持当前所有者体验和权限。

## 6. 数据模型

### 6.1 `venue_members`

新增 `public.venue_members`：

| 字段 | 规则 |
| --- | --- |
| `venue_id` | 引用 `venues(id)`，场所删除时级联删除 |
| `user_id` | 引用 `auth.users(id)`，账号删除时级联删除成员关系 |
| `invited_by` | 引用邀请创建者；MVP 必须是该场所所有者 |
| `joined_at` | 接受邀请的时间，默认数据库当前时间 |

约束与索引：

- 主键为 `(venue_id, user_id)`，一个账号不能重复加入同一场所；
- 禁止 `user_id = venues.owner_id`，由接受邀请 RPC 验证，并以约束触发器防止受信任服务误写；
- 按 `user_id` 建索引，用于场所切换器查询共享场所；
- 最多 4 名成员由事务化 RPC 强制执行，不能依赖前端计数；
- 客户端不能直接 `INSERT`、`UPDATE` 或 `DELETE` 成员关系。

`venue_members` 不存储昵称或头像副本。成员列表 RPC 只向同一场所的当前成员返回公开展示子集：显示名和短时头像 URL；不得暴露原始头像 object key、locale 或其他账号设置。历史活动日志另存操作时的展示快照，以便成员离开后仍可阅读。

### 6.2 `venue_invites`

新增 `public.venue_invites`：

| 字段 | 规则 |
| --- | --- |
| `id` | UUID 主键 |
| `venue_id` | 引用 `venues(id)`，场所删除时级联删除 |
| `created_by` | 邀请创建者，MVP 必须是场所所有者 |
| `token_hash` | 高熵原始令牌的不可逆摘要，唯一；数据库不保存原始令牌 |
| `created_at` | 创建时间 |
| `expires_at` | 固定为创建后 24 小时，不由客户端指定 |
| `accepted_by` | 接受账号；未使用时为空 |
| `accepted_at` | 接受时间；未使用时为空 |
| `revoked_at` | 所有者撤销时间；未撤销时为空 |

约束与索引：

- `token_hash` 唯一；
- `accepted_by` 与 `accepted_at` 必须同时为空或同时非空；
- `accepted_at` 与 `revoked_at` 互斥，已接受的邀请不能再撤销或被其他账号接受；
- 有效邀请定义为：未接受、未撤销且 `expires_at > now()`；
- 建立 `(venue_id, expires_at)` 部分索引，条件仅为 `accepted_at is null and revoked_at is null`；是否过期在查询时比较数据库当前时间，避免把非 immutable 的 `now()` 放进索引谓词；
- 原始令牌使用密码学安全随机源生成，至少 256 bit 熵，只在创建 RPC 返回时出现一次；
- 原始令牌、哈希和完整加入链接不得写入活动日志、分析事件或错误日志。

有效未使用邀请数量不得超过场所剩余席位。创建邀请时先检查席位和当前有效邀请，但接受邀请时仍必须重新原子检查实际成员数量。

### 6.3 现有实体的所有权

本期不将现有实体改为 `venue_id` 所有权。场所下带 `owner_id` 的空间、箱子和媒体继续记录场所所有者；物品等无独立所有者字段的实体继续通过父记录归属。每条共享授权通过实体到场所的关系向上解析：

- 空间通过 `spaces.venue_id`；
- 箱子通过所属空间解析场所；
- 物品通过所属箱子和空间解析场所；
- 媒体、识别结果和收纳会话通过其业务实体解析场所。

任何写入都由数据库从目标场所推导规范 `owner_id`，不能信任客户端提交的所有者 ID。

成员移动箱子或物品时，来源和目标必须属于同一个共享场所。场所所有者可保留既有的跨场所移动能力，但服务端必须同时校验两个场所；活动记录在来源场所显示“移出此场所”，在目标场所显示“移入此场所”，且仅向同时有权访问目标场所的读者展示目标名称，避免泄露私人场所信息。

## 7. 数据库授权架构

### 7.1 访问帮助函数

新增数据库帮助函数：

- `is_venue_owner(p_venue_id)`：当前账号是否为场所所有者；
- `is_venue_member(p_venue_id)`：当前账号是否存在有效成员关系；
- `can_access_venue(p_venue_id)`：所有者或成员；
- `can_edit_venue_content(p_venue_id)`：MVP 与 `can_access_venue` 等价，用于未来角色扩展。

函数必须固定安全 `search_path`、最小化授权，并避免在成员表 RLS 内产生递归。必要的关系判断使用经过审计的 `security definer` 函数；函数不能接受或信任调用方提供的用户 ID，而应使用 `auth.uid()`。

### 7.2 RLS 与 RPC 分工

- 数据库成员关系与 RLS/RPC 是最终权限边界；
- 前端的 `can_*` 字段仅用于隐藏无权限按钮和给出友好提示；
- 简单读取和低风险编辑可通过 RLS 使用场所访问帮助函数；
- 配额、邀请、成员变更、危险删除、AI 扣费和多实体写入必须经过事务化 RPC；
- 成员的字段级编辑使用受控 RPC 或严格的列授权与 trigger；成员永远不能改写 `owner_id`、`venue_id`、跨场所父引用或箱子 `visibility`；
- service role 的写入权限保持最小化，不能让普通客户端直接修改成员或邀请状态。

原有所有者路径必须继续工作。迁移后的策略应表达“所有者保持原权限，成员获得矩阵规定的额外权限”，不能把所有者意外降为普通成员。

共享能力启用前必须逐项审计并改造：场所/空间/箱子/物品列表与详情、`search_my_items`、二维码解析后的私密箱子读取、物品出库/归还/移动、箱子移动与创建、媒体上传/确认/下载、packing session、AI 批量创建及相关删除路径。任一路径仍硬编码 `owner_id = auth.uid()` 时，不得开放邀请入口。

### 7.3 能力摘要

场所详情或独立 RPC 返回当前账号对场所的能力摘要，至少包括：

- `role`: `owner | member`；
- `can_manage_members`；
- `can_delete_venue`；
- `can_delete_space`；
- `can_delete_box`；
- `can_change_box_visibility`；
- `can_use_ai`。

前端消费能力字段，不在不同页面分别猜测 `role`。数据库仍在每次写入时重新校验权限。

### 7.4 受控 API

实现计划应保持以下职责边界；具体 SQL 返回类型可在不改变语义的前提下细化：

- `list_accessible_venues()`：返回当前账号拥有或加入的场所及角色；
- `get_venue_access_summary(p_venue_id)`：返回能力摘要和成员席位；
- `list_venue_members(p_venue_id)`：向当前场所成员返回安全资料子集；
- `create_venue_invite(p_venue_id)`：仅所有者创建邀请；
- `inspect_venue_invite(p_token)`：返回加入页所需的最小安全元数据，不返回成员清单；
- `accept_venue_invite(p_token)`：原子接受并加入；
- `revoke_venue_invite(p_invite_id)`：仅所有者撤销未使用邀请；
- `remove_venue_member(p_venue_id, p_user_id)`：仅所有者移除成员；
- `leave_venue(p_venue_id)`：成员主动退出，所有者调用被拒绝；
- `list_venue_activity(p_venue_id, p_actor_id, p_event_code, p_cursor)`：鉴权后的关键活动游标分页。

这些函数不接收 `owner_id`、`actor_id` 或角色作为可信输入。操作者来自 `auth.uid()`，规范所有者来自目标场所。

## 9. 邀请与加入流程

### 9.1 创建与分享

所有者在“场所设置 → 家庭成员”创建邀请。创建 RPC：

1. 验证当前账号是场所所有者；
2. 获取场所级事务锁；
3. 统计所有者、成员和有效未使用邀请；
4. 无剩余席位时返回 `venue_member_limit_reached`；
5. 生成高熵原始令牌并仅保存哈希；
6. 写入 24 小时有效的邀请；
7. 返回一次性的完整加入 URL 和到期时间。

分享弹窗提供二维码、复制链接和系统分享，并明确显示“仅可使用一次，有效期 24 小时”。关闭弹窗后不保证可再次获取原始链接；所有者可撤销并重新创建邀请。

### 9.2 接受邀请

加入链接使用 `/join/venue#token=<token>`，令牌放在 URL fragment 中，避免发送给 CDN、应用服务器和 `Referer`；客户端读取后只保存在当前标签页内存或 `sessionStorage`，不得写入持久缓存。未登录用户先登录或注册，完成后恢复原加入意图。页面在接受前通过受控 RPC 展示场所名称、所有者昵称和权限摘要，不显示场所物品内容。

接受 RPC：

1. 对原始令牌做相同摘要并查找邀请；
2. 锁定邀请行，并获取场所级事务锁；
3. 邀请已有 `accepted_by` 时：若接受者是当前账号且成员关系仍存在，返回幂等的“已加入”；否则返回 `venue_invite_used`；
4. 邀请未接受时，依次检查已撤销和已过期状态；
5. 验证当前账号不是场所所有者；
6. 当前账号已通过其他邀请成为成员时，返回“已加入”但不消耗这条未使用邀请；
7. 重新统计成员，满 5 人时返回 `venue_member_limit_reached`；
8. 写入 `venue_members`；
9. 在同一事务内标记 `accepted_by` 和 `accepted_at`；
10. 返回场所 ID，由客户端刷新场所列表并进入共享场所。

同一邀请被并发接受时只能有一个账号成功；两个邀请竞争最后一个席位时也只能有一个成功。

### 9.3 邀请状态

加入页必须区分：

- 有效、等待接受；
- 已过期；
- 已使用；
- 已撤销；
- 场所已满；
- 当前账号已是成员；
- 当前账号就是所有者；
- 场所不存在或已删除。

无效状态不泄露成员清单或场所内容。邀请被使用后，即使原接受者随后退出，该邀请也不能再次使用；此时原接受者再次打开链接也显示“邀请已使用”，而不是重新加入。

## 10. 成员管理与撤权

“家庭成员”页面显示头像、昵称、身份、加入时间和席位 `n / 5`。

所有者可以：

- 创建和分享邀请；
- 查看并撤销未使用邀请；
- 移除成员，需确认且明确说明不会删除对方创建的数据。

成员可以：

- 查看成员列表；
- 主动退出场所，需确认且明确说明退出后立即失去访问权。

移除和退出均使用 RPC，在事务内删除成员关系并写入成员变更审计记录。它们不删除场所、空间、箱子、物品、媒体或既有活动日志。

客户端成功后立即移除场所相关缓存并切换到仍有权限的场所；若没有其他场所则进入空状态。数据库授权是即时撤权的保证，因此被移除成员的旧标签页在下一次读取或写入时收到 `venue_access_denied`，随后清理本地场所缓存并跳转。

## 11. 箱子额度与创建

成员创建箱子必须继续经过现有数据库原子创建路径，不能恢复直接 `INSERT`。RPC 保持现有前端入参形态，以目标空间为起点：

1. 加载空间及其场所；
2. 验证操作者是场所所有者或成员；
3. 将配额主体解析为 `venues.owner_id`；
4. 获取该所有者的箱子创建事务锁；
5. 检查该所有者的永久无限箱子权益和全部未删除箱子数量；
6. 免费额度已满时返回现有 `box_limit_reached`；
7. 以场所所有者作为新箱子的 `owner_id`，实际操作者作为活动 `actor_id`；
8. 写入成功后返回箱子。

因此，免费所有者已有 3 个箱子时，成员也不能创建第 4 个；所有者拥有无限箱子权益时，成员无需另购即可在该场所创建。购买入口和账单信息只向所有者显示。

箱子数量仍按所有者所有场所的总箱子数计算，与现有账号级权益定义一致，不按共享场所单独计算。

## 12. AI Credits 与收纳流程

AI Credits 始终归执行 AI 操作的账号：

- 成员发起图片识别、生成收纳建议或其他计费 AI 操作时，扣成员本人余额；
- 所有者发起时扣所有者本人余额；
- 余额不足返回现有 `insufficient_credits`，不得回退扣场所所有者余额；
- AI 结果写入共享场所时，业务数据的 `owner_id` 仍规范化为场所所有者；
- AI 账本和 Stripe Credits 订单不向其他成员公开。

涉及 packing session、识别结果和批量物品创建的 RPC 必须同时验证操作者可访问目标场所，并保证扣费与业务写入的既有事务/幂等语义不被破坏。

## 13. 媒体与对象存储

共享访问不能通过伪造对象路径绕过数据库授权：

- 上传前由服务端/RPC 根据目标实体解析场所及规范所有者；
- 对象 key 由服务端生成或验证，客户端提交的 `owner_id` 和任意前缀不可信；
- 下载签名 URL 前验证当前账号仍可访问对应场所；
- 成员退出或被移除后，不再为其签发新的 URL；
- 已签发短时 URL 遵循现有有效期，不因此扩大数据库权限；
- 删除媒体所依附实体时沿用权限矩阵，成员不能借媒体 API 删除无权删除的箱子或场所资产。

## 14. 关键活动记录

### 14.1 记录范围

MVP 记录以下五类动作：

- 创建物品；
- 移动物品；
- 修改物品数量；
- 删除物品；
- 移动箱子。

不记录普通浏览、搜索、扫码查看、邀请令牌内容或 AI 提示词。成员加入、退出和被移除可写安全审计日志，但不必混入用户的物品流转列表。

### 14.2 日志内容

复用并扩展现有 `activity_logs`：

- 新增可空的 `venue_id` 外键，场所删除时设为空；
- 新增可空枚举 `event_code`，固定为 `item_created`、`item_moved`、`item_quantity_changed`、`item_deleted`、`box_moved`；
- 保留现有 `action`、`entity_type`、`entity_id`、`box_id` 和 `snapshot`，避免破坏既有审计写入；
- `actor_id` 继续记录实际账号；`snapshot.actor_display_name` 保存操作时展示名；
- 建立 `(venue_id, created_at desc, id desc)` 索引，并为成员和动作筛选增加与查询形态一致的索引。

新关键事件必须同时具有 `venue_id`、`event_code`、实际 `actor_id`、实体名称快照和动作所需的结构化前后值。场所活动页只读取这五种 `event_code`；既有无 `event_code` 的通用审计记录继续保留，但不混入产品活动流。

迁移可在仍能解析箱子/空间关系时回填旧记录的 `venue_id`，但不得猜测历史 `event_code`，因此不承诺展示功能上线前的完整关键活动。

动作快照示例：

- 物品移动：来源箱子 ID/名称、目标箱子 ID/名称；
- 数量变化：原数量、新数量；
- 移动箱子：来源空间 ID/名称、目标空间 ID/名称；
- 删除物品：删除前物品名称、数量及所在箱子名称。

快照保证实体被删除或重命名后仍能理解历史。成员离开后，记录使用操作时昵称并附“已离开”，不把 `actor_id` 改写为空。日志不得包含邀请令牌、支付资料、AI 提示词或私密媒体 URL。

日志应与业务修改在同一数据库事务内写入：业务操作失败时不能产生成功记录，日志写入失败时关键业务操作也不能静默成功。现有通用 trigger 与新增事件写入必须去重：同一次业务操作在产品活动流中只能出现一条对应 `event_code` 记录。

`activity_logs` 的新读取策略按 `can_access_venue(venue_id)` 授权；旧记录继续沿用既有所有者访问规则。成员退出后不再能读取该场所日志，留下的成员仍可看到其历史快照。

### 14.3 活动页面

共享场所提供“最近活动”，默认显示最近 50 条关键记录，支持按成员和动作类型筛选，按时间倒序分页加载。示例文案：

- `小林把“露营灯”从“杂物箱”移动到“户外用品箱”`；
- `妈妈将“纸巾”数量从 3 调整为 6`；
- `阿杰把“冬季衣物箱”移动到“卧室顶柜”`。

列表为空、加载失败和无筛选结果需有独立状态。MVP 不做实时推送；用户进入页面或手动刷新时获取最新记录。

## 15. 前端体验

### 15.1 场所切换器

- 当前账号拥有的场所与加入的共享场所统一展示；
- 共享场所显示“家庭共享”标识和所有者昵称；
- 查询 key 必须包含当前用户 ID，或在认证用户变化时清除账号级场所和能力缓存，避免共享设备跨账号短暂显示上一账号的数据；
- 成员关系变化后失效场所列表、当前场所、成员、能力和活动查询。

### 15.2 场所设置

- 所有者可见“家庭成员”、邀请和移除操作；
- 成员可见成员列表和“退出场所”；
- 所有者专属的删除场所、账单、箱子权益、箱子/空间删除及可见性按钮对成员隐藏；
- 即使前端状态过期，数据库错误仍转换成明确提示并刷新能力摘要。

### 15.3 加入与移动端

- 加入页可在登录前打开，认证后恢复原令牌；
- 二维码在常见手机宽度可完整扫描，复制和分享按钮满足最小 44px 触控区域；
- 弹窗支持 Escape、焦点圈定、焦点恢复、滚动锁定、安全区和 reduced motion；
- 删除、退出和移除确认使用明确对象名称，避免误操作。

所有中英文用户可见文本进入统一 i18n 资源，不在组件内硬编码。

## 16. 稳定错误契约

| 错误码 | 含义 | 客户端处理 |
| --- | --- | --- |
| `venue_invite_expired` | 邀请超过 24 小时 | 显示已过期，请联系所有者重新邀请 |
| `venue_invite_used` | 邀请已被接受 | 显示已使用，不允许再次提交 |
| `venue_invite_revoked` | 所有者已撤销邀请 | 显示邀请已失效 |
| `venue_member_limit_reached` | 场所已达 5 人或无可用邀请席位 | 显示场所已满，所有者可先移除成员/撤销邀请 |
| `venue_access_denied` | 当前账号不再拥有场所访问权 | 清理场所缓存并跳转 |
| `venue_owner_required` | 操作仅允许场所所有者 | 刷新能力并显示无权限 |
| `box_limit_reached` | 所有者箱子额度已满 | 成员提示联系所有者；所有者显示现有付费墙 |
| `insufficient_credits` | 操作者自己的 AI Credits 不足 | 显示本人 Credits 购买入口 |

客户端通过稳定错误码处理，不匹配完整数据库或英文错误文案。未知错误显示非破坏性通用提示并保留用户输入。

## 17. 并发、安全与隐私

- 邀请创建、接受、撤销、成员退出和移除均为数据库事务；
- 邀请接受锁定邀请行，并以场所级 advisory lock 或等价行锁串行化人数检查；
- 两个邀请竞争最后席位时，事务完成后重新计数，不能依赖开始时快照；
- 成员创建箱子沿用所有者级事务锁，不能并发突破免费额度；
- 所有授权从 `auth.uid()` 和数据库关系推导；客户端角色、所有者 ID、席位数和能力均不可信；
- 邀请 token 只存哈希，日志进行字段白名单过滤；
- RLS 覆盖读取，RPC 覆盖跨实体写入和危险动作；测试必须证明直接 REST 调用不能绕过；
- 移除成员不删除日志，满足共同数据连续性；账号资料删除时历史日志保留展示快照，并按既有隐私规则处理主体 ID；
- 成员不能看到所有者或其他成员的账单、Credits 余额、Stripe Customer、其他场所或私密账号资料。

## 18. 可观测性

服务端记录稳定结果码和匿名化标识，至少覆盖：

- 邀请创建成功/席位不足；
- 邀请接受成功、过期、已使用、已撤销、场所已满；
- 成员加入、退出和被移除；
- 共享访问被拒绝；
- 成员创建箱子被所有者额度阻止；
- 活动日志事务失败。

监控重点：邀请接受异常率、重复/并发冲突、成员人数超过约束的异常数据、撤权后仍成功访问的安全告警、活动写入失败。日志不记录原始邀请 token、完整加入 URL、物品私密内容或支付数据。

本期不假设已接入产品分析平台，不声称具备邀请转化漏斗；发布手册应提供可执行的数据库健康检查查询。

## 19. 迁移与发布

采用向前兼容的分阶段发布：

1. 添加成员、邀请表、索引和访问帮助函数；此时不改变旧前端行为；
2. 添加邀请/成员 RPC、场所能力摘要和数据库测试；
3. 扩展读取 RLS，使成员可访问共享场所内容；
4. 改造箱子、物品、媒体、packing 和 AI 写入路径，确保规范所有者与实际操作者分离；
5. 发布前端场所切换器、成员管理、加入页和能力控制；
6. 开启邀请入口，先内部账号验证，再逐步开放；
7. 发布活动记录页面及筛选。

发布时必须先保证数据库可接受新客户端调用，再发布前端。扩展 RLS 前完成越权测试；开启入口前验证所有写路径均不再假设 `auth.uid() = owner_id`。

回滚优先关闭前端邀请入口并保留成员、邀请和日志数据。若需要回退前端，不删除成员关系或共享数据；通过向前迁移临时收紧新增共享操作，同时保持现有成员的安全读取或明确维护状态。绝不通过删除成员表或改写业务 `owner_id` 回滚。

## 20. 测试策略

### 20.1 数据库与权限

- 所有者原有场所行为完全不变；
- 成员可读取和编辑共享场所，但不能读取未共享场所；
- 成员可删除物品，不能删除箱子、空间或场所；
- 成员不能修改箱子公开/私密状态；
- 成员不能直接修改成员、邀请、账单或权益；
- direct REST 写入不能绕过 RPC 和权限矩阵；
- 被移除成员的旧会话下一次请求返回 `venue_access_denied`。

### 20.2 邀请与并发

- 有效邀请正常加入；
- 未登录后登录可恢复加入；
- 过期、撤销、已使用邀请分别返回稳定错误；
- 同一邀请并发接受只能一次成功；
- 两个邀请竞争最后席位只能一人成功；
- 已是成员重复接受为幂等结果；
- 所有者不能接受自己的邀请；
- 满 5 人不能创建或接受新邀请；
- 移除成员后可创建新邀请，但旧邀请不能复用。

### 20.3 箱子与 Credits

- 成员创建箱子写入所有者 `owner_id` 和成员 `actor_id`；
- 免费所有者已有 2 个箱子时，并发创建不会超过 3 个；
- 免费所有者已有 3 个箱子时成员收到 `box_limit_reached`；
- 无限箱子所有者的成员可创建第 4、5 个箱子；
- 成员 AI 操作只扣成员本人 Credits；
- 成员余额不足不扣所有者，也不写入不完整结果。

### 20.4 活动记录

- 五类关键动作均记录实际操作者；
- 移动物品和箱子包含正确来源/目标；
- 数量变更包含正确前后值；
- 删除物品后仍能通过快照渲染名称；
- 成员退出后显示历史昵称和“已离开”；
- 业务事务失败不产生成功日志；
- 成员和动作筛选、分页顺序正确。

### 20.5 前端与端到端

- 所有者邀请 → 成员登录接受 → 场所切换器出现共享场所；
- 成员完成搜索、扫码、移动物品和创建箱子；
- 无权限按钮不可见，直接请求仍被数据库拒绝；
- 成员被移除后当前页安全跳转；
- 共享设备账号切换不显示上一账号的场所缓存；
- 手机二维码、成员管理、退出确认、焦点和键盘操作通过；
- 中英文文案及错误状态完整；
- 既有公开搜索、箱子权益、AI Credits 和单人场所回归通过。

## 21. 验收标准

功能完成必须同时满足：

1. 场所所有者能生成单次、24 小时有效的链接或二维码；
2. 家人使用自己的账号直接加入，场所总人数不会超过 5；
3. 成员可独立完成“搜索 → 扫码 → 将物品移到另一箱子 → 创建箱子”；
4. 成员能删除物品，但不能删除箱子、空间或场所，也不能管理账单和成员；
5. 成员创建箱子准确使用所有者额度，AI 操作准确使用成员本人 Credits；
6. 所有者能在最近活动中看到实际操作者及完整前后位置/数量；
7. 所有者移除成员或成员退出后，访问权立即失效；
8. 撤权不会删除任何场所数据或历史记录；
9. 并发接受邀请和并发创建箱子不能突破人数或免费额度；
10. 原有单人场所、公开搜索、支付与 AI Credits 行为无回归。

## 22. 后续迭代

MVP 稳定后可按以下顺序扩展：

1. 关键活动的站内或推送通知；
2. 所有权转让与更完整的离场流程；
3. 只读成员、儿童成员、管理员等细粒度角色；
4. 家庭共享 AI Credits 或预算；
5. 多场所家庭工作区及跨场所成员管理；
6. 更完整的审计导出与恢复能力。

这些扩展不改变本期的基本原则：场所是共享边界、数据库是授权权威、操作者与数据所有者分别记录。
